# 02 — IPC, authority and native operating-system integration

## 1. Begin with a request, not a permission

Suppose the conversation interface wants to export a chat. The convenient API is `writeFile(path, text)`. The safer application operation is `exportConversation(conversationId)`. The first gives the renderer broad authority over arbitrary paths and contents. The second lets the main process fetch the authorized conversation, open a save dialog and write an approved representation. Good desktop APIs express the user's intention rather than expose the operating system directly.

The renderer is not the user. It is code acting through a user interface, and that code may process untrusted material. A malicious document could exploit a rendering mistake and call every exposed method. Your bridge design determines the damage possible after that mistake. Narrow interfaces make the resulting attack surface smaller and easier to review.

A capability is permission to perform a bounded operation on a bounded resource. A workspace identifier can refer to a root folder the user selected. A proposal identifier can refer to one tool action awaiting approval. These identifiers should map to main-process records rather than let the renderer reconstruct unrestricted paths. An opaque identifier is not itself authentication; still check which window and account owns it.

Electron's [security guide](https://www.electronjs.org/docs/latest/tutorial/security) is the baseline reference. The course's threat model adds agent-specific concerns: imported text, model output, tool proposals and plugin descriptions are all data from outside your authority boundary. A tool proposal is not authorization just because it was generated by your preferred model.

## 2. Design the bridge as a small application API

Use request/response IPC for operations with a defined result and event streams for ongoing progress. Avoid synchronous IPC for routine work; it couples responsiveness to the receiving process. Do not expose a generic channel name supplied by renderer code. Every bridge method should select its own fixed channel.

This is a **preload fragment**, intended for the generated preload entry:

```ts
import { contextBridge, ipcRenderer } from 'electron';

contextBridge.exposeInMainWorld('desktop', {
  chooseWorkspace: () => ipcRenderer.invoke('workspace:choose'),
  listFiles: (workspaceId: string) =>
    ipcRenderer.invoke('workspace:list', { workspaceId }),
  onRunEvent: (receive: (event: unknown) => void) => {
    const listener = (_event: Electron.IpcRendererEvent, value: unknown) => {
      receive(value);
    };
    ipcRenderer.on('run:event', listener);
    return () => ipcRenderer.removeListener('run:event', listener);
  }
});
```

The callback receives only the data value, not Electron's IPC event. The returned function removes exactly the listener registered by this subscription. Passing `ipcRenderer` itself or an arbitrary `invoke(channel, args)` through the bridge would undermine this design. The [contextBridge reference](https://www.electronjs.org/docs/latest/api/context-bridge) describes supported values and isolation behavior.

A TypeScript declaration tells the renderer what exists on `window.desktop`, but it does not install anything. The preload installs the implementation. Keep declaration and implementation aligned. One useful pattern is a shared type-only package containing data contracts and bridge signatures, with no Electron or Node imports exposed to the renderer runtime.

Events need validation on the receiving side too. A utility process might crash, run an incompatible version or emit malformed data. Decode events before applying them to UI state. Add a protocol version and reject unknown versions explicitly rather than interpreting a new shape as an old event.

## 3. Validate sender, frame and payload separately

There are three different questions: which `webContents` sent a request, which frame in that content sent it, and what the payload means. Answering only one leaves gaps. An approved window can contain an untrusted iframe, and a correctly shaped payload can still come from the wrong window.

The companion includes a concrete sender check. This **main-process fragment** illustrates the pattern for a single trusted window:

```ts
import { ipcMain, type IpcMainInvokeEvent, type BrowserWindow } from 'electron';

function assertTrustedCaller(event: IpcMainInvokeEvent, window: BrowserWindow) {
  if (event.sender !== window.webContents) throw new Error('UNTRUSTED_CALLER');
  if (!event.senderFrame || event.senderFrame !== window.webContents.mainFrame) {
    throw new Error('UNTRUSTED_FRAME');
  }
  const caller = new URL(event.senderFrame.url);
  if (caller.protocol !== 'atlas:' || caller.hostname !== 'app') {
    throw new Error('UNTRUSTED_ORIGIN');
  }
}

function parseWorkspaceRequest(value: unknown): { workspaceId: string } {
  if (!value || typeof value !== 'object' || Array.isArray(value)) {
    throw new Error('INVALID_REQUEST');
  }
  const candidate = value as Record<string, unknown>;
  if (typeof candidate.workspaceId !== 'string' ||
      !/^[a-zA-Z0-9_-]{1,80}$/.test(candidate.workspaceId)) {
    throw new Error('INVALID_WORKSPACE');
  }
  return { workspaceId: candidate.workspaceId };
}
```

In development, add only the exact expected loopback origin for your own server. Do not authorize every `http:` URL or every port on localhost. In a multiwindow app, use a registry mapping each trusted content object to allowed capabilities. A settings window and a document preview may intentionally have different rights.

Runtime schema libraries can make decoding clearer, but no library can infer the authorization policy for you. After decoding a workspace identifier, look up its owner and permitted operations. Limit strings, array lengths, attachment sizes and concurrent requests. A well-typed request can still exhaust memory if it contains a million allowed items.

Use [ipcMain](https://www.electronjs.org/docs/latest/api/ipc-main) handlers as adapters. Translate request data into a domain operation and convert expected failures into safe result objects. Do not place all business rules directly in the handler; a thin adapter is easier to test and reuse from menus or background tasks.

## 4. Streaming without accidental leaks

A chat run can produce many events: started, text delta, tool proposal, approval result, tool output and completion. Each event needs a run identifier and sequence number. A renderer should ignore events for a conversation it no longer owns or has unsubscribed from. A late completion must not overwrite a newer run's state.

Keep a bounded buffer. If the renderer is slow, the producer must either pause, coalesce deltas, spill durable events to storage or terminate with a clear limit. An unbounded JavaScript array is not a streaming design. Small text fragments can be batched at a display-friendly frequency while durable state records larger meaningful transitions.

Message ports are useful for high-volume communication, but they do not replace schemas or authorization. Transfer a port only to a trusted recipient and close it when its owner disappears. Decide how the receiver requests resynchronization after missing events. A snapshot plus “events after sequence N” is usually easier to reason about than an undocumented mixture of mutable objects and callbacks.

Errors and cancellation are events too. A cancelled run should reach a terminal state exactly once, even when the provider produces one last chunk. Define which terminal outcome wins and enforce it centrally. Removing a visual spinner does not cancel a network request or stop a native subprocess.

## 5. Local content protocols and navigation

Prefer a deliberately registered application protocol for packaged content rather than casually granting `file:` pages broad behavior. Register scheme privileges before application readiness as documented, then install handlers after readiness. Serve only packaged assets that you intend to expose. A protocol handler is a small local server and deserves the same path discipline as an HTTP route.

A robust simple design uses a manifest: URL path keys map to exact packaged filenames and MIME types. Unknown paths return 404. This avoids deriving arbitrary filesystem paths from URL text. A larger application can generate the manifest at build time from renderer output. The companion uses a tiny fixed mapping for its three renderer assets.

With a path-derived handler, decode and normalize carefully, reject traversal and confirm canonical containment. URL normalization can remove dot segments before your code sees them, so do not rely on one regular expression as your entire defense. Never map a hostname or query parameter directly to a disk root. See [protocol](https://www.electronjs.org/docs/latest/api/protocol) for session-specific registration behavior.

Set a restrictive production content security policy. Allow only the scripts, styles, images and connection destinations your application needs. If your renderer does not talk directly to providers, its `connect-src` can remain very narrow. Development hot reload may need a separate policy; document it and ensure production cannot inherit a broad development exception.

Intercept unexpected navigation and new-window requests. Parse external links as URLs, allow only approved schemes and destinations, and open them through a main-process operation after validation. An `https:` string is not automatically a safe destination if it points to an attacker-controlled endpoint receiving private query data.

## 6. Filesystem authority and its sharp edges

A user-selected workspace grants a specific scope. Store the canonical root and derive relative paths within it. Reject absolute paths, parent traversal, empty forbidden paths and unexpected separators. On Windows, consider drive letters, UNC paths, reserved names and case behavior. On Unix-like systems, symbolic links can escape a root even when a textual path appears contained.

Canonical-path checks improve a trusted workspace implementation but do not fully eliminate time-of-check/time-of-use races. Another process can change a symlink after you inspect it. For hostile writable trees or arbitrary agent code, an OS-level sandbox with constrained mounts is stronger than repeatedly calling `realpath`. Describe the guarantee honestly: a convenience path guard is not a universal filesystem security boundary.

Separate read and write grants. Listing files should not imply permission to delete a project. For a write proposal, show the exact target, operation and proposed diff. Hash or otherwise bind the approved proposal to the content that will be executed. If the content changes, request a new approval. Never let an approval for “format this file” silently expand into “replace every file in the workspace.”

For exports, use an OS save dialog and an atomic write strategy where possible. Write to a temporary file in the target directory, flush as required by the durability goal and rename into place. Handle overwrite decisions explicitly. Atomic rename helps avoid partial visible files; it does not make every multi-file operation transactional.

## 7. Windows as native resources

`BrowserWindow` combines a native window and web content. `BaseWindow`, `View` and `WebContentsView` support more explicit composition. Prefer current APIs for new work; `BrowserView` is a legacy migration topic. Embedded views need their own lifecycle cleanup and content policies.

A trusted application window can contain the chat interface while a separate unprivileged preview shows a remote page. The preview should have no application bridge, an isolated session, constrained navigation and explicitly denied permissions unless the user grants a needed capability. Sandboxing and context isolation are necessary foundations, but remote content must also be prevented from invoking privileged host behavior indirectly.

Persist window bounds carefully. A user can disconnect a monitor between launches; saved coordinates may now be offscreen. Compare saved bounds with current displays and move or resize into a visible work area. Respect display scaling and minimum sizes. Restore maximized state separately from normal bounds so a maximized shutdown does not overwrite a useful restore size.

Frameless windows create extra responsibilities: drag regions, accessible controls, double-click behavior, native menus and platform conventions. Use a native frame first. If the product later needs a custom titlebar, test it with keyboard navigation, screen readers, high contrast, multiple displays and OS snapping behavior. Styling a web header does not automatically recreate a desktop titlebar.

## 8. Menus, shortcuts, tray and notifications

Menus are more than decorative duplication. They expose discoverable commands, platform conventions and keyboard access. Use roles for standard editing operations when appropriate and route application commands through the same domain services as buttons. A menu item should not bypass a disabled-state rule applied in the React interface.

A local shortcut is active within the application; a global shortcut can conflict with other programs and may fail to register. Check registration results and let users choose alternatives. Clean up registrations during shutdown. A background agent application should not reserve common system combinations merely because they work on a developer's machine.

Tray icons can support background work, but they introduce ambiguous lifetime expectations. Explain whether closing a window quits or hides the application. Provide a visible quit command. Keep the tray object alive and update its menu from authoritative service state. On Linux, behavior varies by desktop environment, so offer a window-based route to the same functionality.

Notifications should announce useful state without exposing private conversation text on a lock screen. Clicking one should focus the right window and conversation. Reconstruct this navigation from a validated identifier rather than a privileged URL containing credentials. Native permission and support differences need graceful fallback to in-app status.

## 9. Clipboard, images, screens and accessibility permissions

Clipboard operations can leak data across applications. Make writes user-initiated and avoid polling the clipboard as a default agent capability. Rich text, HTML and image clipboard formats need separate treatment. Plain text is often the safest export for an initial version.

Use `nativeImage` for appropriate image conversion and native icon integration, and understand the difference between image dimensions and display scaling. A missing image path may result in an empty image rather than the exception you expected; validate assets during packaging. Large images need size limits before decoding and should not be repeatedly serialized across IPC.

Screen and window capture requires a clear permission and consent flow. Capture only what the user selected, display an attachment preview and explain when image data leaves the device. Do not implement capture as an invisible side effect of a global shortcut. Handle permission denial, missing capture sources and OS changes without escalating to broad unrelated privileges.

Some features require platform-specific accessibility or automation permissions. Request them at the point of use and explain the exact feature. A desktop agent should remain useful when a user refuses screen capture or automation. “Enable every permission to continue” is usually an unnecessary loss of trust and a poor diagnostic design.

## 10. Sessions, networking and permissions

A session owns browser storage, cookies, permissions and network-related behavior. Separate sessions when content has different trust or identity requirements. Use persistent partitions only when persistence is intended. A remote preview should not inherit privileged application cookies merely because sharing a session is convenient.

Install permission request and permission check handlers for sessions that load web content. Default to denial, then grant a specific permission only for a specific origin and user action. Handle display media, microphone, camera, geolocation and notification requests as distinct capabilities. A wildcard approval function makes an unrelated embedded document a route to native access.

Electron networking APIs and Node's networking stack can behave differently around proxies, cookies and certificate handling. Choose the stack intentionally for each operation. Do not disable certificate validation to make a corporate proxy problem disappear. Provide diagnostics explaining which host failed and which network path the application used, without collecting access tokens or entire private URLs.

Downloads are file writes. Validate the initiating origin, filename and destination, show progress and support cancellation. Do not automatically open downloaded executables. For agent runtime downloads, verify publisher signatures or a trusted manifest before installation, and apply the same update ownership discipline taught in chapter 07.

## 11. Fuses and dependency boundaries

Fuses disable selected Electron binary capabilities at packaging time. Review the available options for the pinned runtime and flip them before signing. Disabling the run-as-Node path can affect `child_process.fork`, so the agent architecture should use a compatible process strategy. See [Electron fuses](https://www.electronjs.org/docs/latest/tutorial/fuses).

An agent app may legitimately need a bundled helper runtime, but it should not casually depend on launching its signed UI binary as a general interpreter. Separate the helper, its signature, its update channel and its capabilities. A locked-down desktop shell and a controlled sandbox runner have different responsibilities.

Third-party dependencies are part of the trusted computing base. A Markdown renderer, native SQLite package and updater library occupy different risk positions. Review maintenance, compatibility, license and integration behavior rather than counting download statistics. Pin versions and monitor security updates; a lockfile is reproducibility evidence, not proof that dependencies are safe.

Do not load arbitrary JavaScript plugins in the main process and describe them as harmless extensions. A main-process plugin has application authority. Safer extension models use declarative contributions or separate constrained processes with explicit capabilities. The chapter 05 plugin contract carries this principle into agent tools.

## 12. Guided native-feature laboratory

First implement export through a domain operation. The UI selects a conversation, the main process verifies ownership, the OS dialog selects a path and the repository returns content. Make the cancelled-dialog path a normal result. Confirm the renderer cannot choose an unrelated filesystem target by modifying an IPC request.

Next add one trusted window and one untrusted preview. Give the preview no preload bridge. Attempt navigation from each view and confirm the policy. Test an iframe in the trusted window; it must not inherit authorization merely because its enclosing `webContents` is trusted. Record precisely which sender checks rejected it.

Then add menus, a configurable global shortcut, a tray menu and a privacy-preserving notification. Deliberately choose a shortcut already in use and handle registration failure. Close the main window during a job and reopen it from the tray. The job state should live in a service and reappear correctly.

Finally add workspace browsing with an explicit root grant. Test a normal relative path, parent traversal, an absolute path, a symbolic link outside the root, a missing file and a permission-denied file. Do not accept a passed test on one OS as proof for all path semantics. Capture platform-specific differences in a short evidence record.

## 13. Debugging and practical extensions

A request that never resolves can mean the handler was never registered, the main process blocked, a dialog is waiting behind another window or an exception escaped a wrapper. Add time-bounded diagnostics with a correlation ID. A timeout should not automatically repeat a destructive operation; the original may still be running.

A renderer that receives events twice may have two listeners, two windows sharing a subscription or a development effect mounting twice without cleanup. Inspect registration ownership before adding a boolean to suppress all future events. A correct cleanup strategy scales better than a global “already subscribed” flag.

For an extension, implement capability records with expiry and account ownership. A grant for workspace W in account A should become invalid after account switching, and a renderer should receive a recoverable “grant expired” result rather than an arbitrary native exception. This connects native authority to the identity lifecycle you will study later.

Completion evidence includes the bridge contract, sender and payload tests, a native-feature demo, a path-behavior matrix, a session permission policy and a written list of remaining OS-level risks. You are learning to design bounded native functionality, not simply to memorize Electron method names. The next chapter builds a useful local workspace on top of these bounded operations.

## 14. Worked native resource example: a command service

Imagine implementing “Stop current run” in a button, a menu and a tray item. Three independent handlers may drift: the button respects a terminal state, the menu sends cancellation without an ID and the tray kills a worker directly. Instead, define one application command with a stable input contract. Every presentation surface calls that command, which validates ownership and applies the same transition.

A **TypeScript service fragment** illustrates the structure:

```ts
type RunRecord = { id: string; owner: string; terminal: boolean };
type CancelResult = 'cancelled' | 'already-finished' | 'not-found';

export class RunCommands {
  constructor(
    private readonly find: (id: string) => RunRecord | undefined,
    private readonly requestStop: (id: string) => void
  ) {}
  cancel(owner: string, id: string): CancelResult {
    const run = this.find(id);
    if (!run || run.owner !== owner) return 'not-found';
    if (run.terminal) return 'already-finished';
    this.requestStop(id);
    return 'cancelled';
  }
}
```

Returning `not-found` for another owner's record avoids revealing its existence through this interface. A production service also needs an atomic transition so two cancellation callers cannot race with completion. The example's purpose is to show placement of policy, not to replace the full run model.

The IPC adapter decodes an identifier and establishes the caller's owner. A menu handler obtains the active authorized context from the application. A tray handler targets an explicit selected job or asks the user to open the app. None should infer authority from whichever global variable happens to contain a last-used run ID.

## 15. Lesser-used native capabilities still need ownership

Printing can be useful for report exports. A print request should select an authorized document, render a controlled representation and show appropriate options. Printing an untrusted remote page is a different feature from exporting your own report. For PDF output, bound document size and account for fonts, pagination and blocked remote resources.

Drag-and-drop has both browser and native aspects. Dropping a file into the renderer should create an import request, not imply that all neighboring directories are authorized. Modern Electron exposes file-path helpers through the supported preload route; do not retain obsolete assumptions about arbitrary `File.path` behavior from older tutorials. Validate file type and size in the privileged service before parsing it.

System theme changes should update both the interface and native assets where needed. A stored preference may mean light, dark or follow system; keep those three states distinct. A high-contrast mode and reduced-motion preference deserve deliberate handling rather than simply swapping a CSS color variable.

Power and thermal signals can affect long-running jobs. If a machine is on battery or resumes from suspend, reconsider expensive indexing and reconnect providers carefully. Do not interpret wake as permission to replay every queued external action. The job's authority and relevance may have changed while the laptop slept.

Push notifications, shared textures, platform sharing menus and touch-bar integrations are specialized surfaces. The API atlas maps them to their official references and application exercises. Implement them when the product benefits, with a platform availability check and a useful fallback. Expertise includes knowing when a specialized API creates maintenance cost without improving the user's main workflow.

## 16. A review procedure for a newly added capability

For every new bridge method, write four sentences: which user action motivates it; which resource it can affect; which process owns that resource; and what a compromised renderer can request. Then add input limits, owner checks and a terminal cleanup path. This is a focused implementation aid, not a reason to stop ordinary work for a broad hypothetical review.

For a new embedded view, record its session, preload, navigation policy, permission policy and destruction owner. For a new background task, record its cancellation signal and durable recovery state. For a new native executable, record its publisher, package location, update owner and effective OS permissions. These concrete records catch integration mistakes that are difficult to see from a screenshot.

## 17. Boundary versioning during upgrades

A preload and renderer usually ship together, but an external worker or cached remote interface may not. Include a small handshake that identifies protocol version and supported operations. Refuse incompatible combinations with an actionable message instead of trying to reinterpret unknown events. Compatibility failures are easier to support when the interface names the two versions involved.

Additive fields can often be ignored by an older decoder if the contract permits them. New event kinds and changed meanings require deliberate versioning. Never reuse a channel name for a different authority level without reviewing every caller. A stable name should describe stable behavior; otherwise it creates the appearance of compatibility while changing what a caller is allowed to do.

This also applies to persisted grants. A grant issued for a read-only tool must not become write permission after a plugin upgrade redefines the same tool identifier. Bind grants to capability meaning, version and scope, and invalidate them when those properties change.
