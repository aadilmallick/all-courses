## Status checked November 13, 2026

Vibe Kanban is an important agent-orchestration and review tool to recognize, but older cloud tutorials need a major qualification. On April 10, 2026, the company behind it announced its shutdown and said the project would continue as open source and community maintained. The announcement described a thirty-day period for remote services, their removal, and continued local workspace operation. [Official shutdown announcement](https://www.vibekanban.com/blog/shutdown).

This is a lifecycle and migration reference, not a full active-service course chapter. It is deliberately outside the thirty-two core tool guides. Do not follow an older instruction to buy or configure the former hosted team service as though that were a maintained new-adoption path.

## What to check before using local workspaces

Open the [official source repository](https://github.com/BloopAI/vibe-kanban), read its current README and release notes, and identify the version you intend to run. Check which features are local and which previously depended on removed remote services. Source availability does not guarantee that every old screenshot still describes a working feature or that commercial support remains available.

Use a dedicated training repository and an already-understood coding agent. Launch only through the currently documented installation path. Confirm the project folder, branch/workspace behavior, and check command before delegating a small task. Review the diff and export important results to your repository. Treat the board as a control surface, not as the only copy of task history.

## How to read an older tutorial critically

Separate the durable idea from the retired product path. Planning a task, creating an isolated working copy, launching an agent, reviewing the patch, and checking the result remain useful concepts. Organization creation, shared cloud issue state, and remote service setup must be checked against the shutdown notice and current source.

If a tutorial's key workflow requires a removed service, stop that tutorial at the concept level and use a maintained alternative for practice. [Paradev](/factories/paradev/) is this curriculum's active task-board/workspace chapter on supported platforms. [OpenHands](/factories/openhands/) teaches a composable control surface, and [Factory](/factories/factory/) teaches structured orchestration. These are different operating models, not drop-in migration promises.

## A small migration inventory

List the information you need to preserve: task descriptions, acceptance criteria, comments that contain decisions, workspace paths, branches, uncommitted files, and links to review artifacts. Export using supported facilities where still available. Inspect the export before deleting or abandoning an old installation. A successful file download is not proof that every important field was included.

Choose one representative task and reconstruct it in the replacement workflow. Verify its context, workspace, agent access, checks, and delivery. Only then migrate the rest of the queue. This small comparison exposes missing metadata and changed assumptions without turning the whole backlog into an experiment.
